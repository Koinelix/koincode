# Wallet core

`@koincode/wallet/protected-host` is the independent sealed Host's private physical connection entry. It loads only the fixed protected native addon, whose actual bootstrap verifies root-held receipt/installation lease, formal code, console and connected original broker before exposing a C-wrapped owner. Importing the entry, constructing a lookalike object, or receiving transport hello never proves a ready profile, authentication or source/payment capability. The legacy node/host/default exports and payer remain unchanged. The same original `GeneralSessionChannel` owns request correlation; a native-only Duplex moves bounded frames without exposing a numeric socket or idle reads. Every fragment of protected reply ingress uses `recvmsg` and rejects all rights. Cancellation waits for the actual original callbacks; uncertain native close remains uncertain even if the JS stream emitted close. The outer broker must independently drain actual IO and reap the original child before releasing its UID owner.

Native window registration binds the original AppKit view/window and the actual onscreen WindowServer ID/PID; supplied addresses are compared with real objects, never dereferenced. The fixed `window.ready` wire contains only a positive uint32 ID, uses operationId=sessionId and carries no value. Native guard state only prevents repeat attempts, tracks cancellation and retains unknown completion; it cannot authenticate or authorize material. The broker separately verifies the same unreaped child and full audit token. Private SQLite remains pinned to 3.54.1; the native bridge uses the locked Electron 41.0.3/NAPI 10 header set and exports only the two required NAPI registration symbols. The same bridge now owns the original native resource/repository factory, actual commit FD loans and fixed SQL ports. The native management-record backend and broker session actor exist as private components; the public control loop, sealed manager runtime/build and actual admission/acceptance remain incomplete.

The private native metadata reader requires a sealed MATCHED accepted-prefix replay, its exact original anchor identity, the current actual non-root installation and a precisely scoped committed reference. It uses an explicit metadata allowlist; source keys, signed bytes, native-resource references and unknown references are not admitted through this reader. Unregistered and unsettled references perform no Keychain IO and never mean missing/create. The fixed noninteractive DP query checks all original namespace attributes and the complete raw body SHA-256 against the accepted committed event. A missing or changed committed item is conflict. The one-call, at-most-1-MiB read retains synchronous IO ownership and its original 30-second monotonic/lifetime budget; late output is discarded and owned byte copies are wiped on failure or destroy. These privacy-bearing bytes remain inside the protected actor. A matched snapshot or read does not prove native provenance, record-specific semantics, current resource ownership, target readiness, material authority or signing; genuine parent/backend gates remain required. There is no write, delete, fallback, enumeration or retry, and no legacy Skill dependency.

The internal macOS general-wallet identity preflight also verifies the protected host framework's complete nine-fuse Electron 41 profile across every Mach-O slice and reads the actual socket peer's bounded kernel argument record. It admits only the fixed host executable with no extra arguments. Kernel arguments are defense in depth, not immutable launch provenance; an omitted environment is not proof of sanitization. These checks do not grant secret admission. The legacy Skill host, helpers, grants, budgets and public client contracts remain separate.

Manual-transfer approval passes its own frozen full preview to the private host authentication callback after human confirmation. The native authentication scope binds that preview's account, complete digest and unsigned fields; native validation recomputes the digest and integer maximum fee before producing a fixed-resource localized reason. This request is capped at 32 KiB and returns no unsigned encoding, keys, signed bytes or capability. Success remains subject to the original approval lifetime, protected risk and signing checks. Base Sepolia remains reserved and OP-stack manual fee authorization remains unavailable. This internal scope does not change the Skill payment contract or its budgets.

The private desktop confirmation adapter renders only a strict display projection in its own sandbox window. It returns a boolean, never a signing capability or system-authentication fact. It must share the protected approval owner's monotonic clock and genuine native lifetime; ordinary asset IPC, SDK/MCP and Skill entrypoints cannot invoke it. Acceptance requires its own focused top-level sender and exact request/digest. Blur, expiry, cancellation and native invalidation close the display. The adapter remains disconnected from product secret admission until the real protected host is assembled.

The manual approval owner cancels both confirmation and authentication at the earliest intent, quote or simulation deadline. It also checks that deadline and monotonic clock after callbacks, regardless of timer delivery. An abort requests cancellation; it does not prove native work has drained. The owner retains its active slot until the original callback settles, rejects late success and clears only its own timer on completion. Issued evidence retains its original deadline and consumption checks. This does not change legacy Skill timeouts or admission.

The internal `GeneralWalletRuntime.openProtectedSession` owns one sensitive management session with setup commands and scoped, read-only manual history. History resolves a source ID through that runtime, reads the existing protected journal and recovery projections, and returns only bounded display fields. Unregistered streams, missing material and unknown broadcast outcomes remain explicit; absent creation times stay null and risks are retained. It returns no intent encoding, signed bytes or key references and performs no RPC, stream creation or broadcast. Pagination binds the original head. Runtime close revokes and drains its single in-flight read before releasing the journal and state owner. This session is not part of the public SDK, MCP or ordinary asset IPC and does not affect Skill payment state.

The private restore management controller owns only one UI request, one frozen validated plan copy and an exact single-use password challenge. The genuine parent selects and retains the stable backup file, establishes native authentication, and calls the password prompt only after that scope is current. A fixed private window notification carries request/challenge IDs and stage; it is not native authorization or a transferable capability. The existing management session permits only that matching password/cancel control while restore work occupies its sole business slot. The preview returns bounded source address/type/status/selection and plan classification/counts, never the full plan, history, path, key reference or cryptographic material. Explicit publish reuses that frozen plan through the original coordinator; only a strict correlated reopened result crosses the UI boundary. Unknown or late publication is inspection-required, never a rollback or automatic retry. Closing drains the actual child operation before the parent and refuses to report release on unknown effects. These private UI ports do not assemble the production Host or grant first-restore admission; no empty runtime is created to render this flow. Legacy Skill APIs, ownership and budgets remain unchanged.

The internal general-wallet backup worker uses the distinct `koincode-general-wallet` payload v1 and `koincode-general-wallet-backup+jwe` type. It checks exact selected source and pending-key coverage, all known history and signing heads, source commitments, decrypted address/path and the original setup input binding. Existing state, history and keystore validators remain authoritative. PBES2-HS512+A256KW/A256GCM uses the fixed bounded password policy and KDF parameters; legacy and general types reject each other. This validates an encrypted snapshot, not latest signing continuity or restore authority. Its decrypted result contains secret wrapping keys and must remain inside the protected restore owner, never a renderer, ordinary asset IPC, SDK, MCP or model response. Native authorization, consistent snapshot collection and durable file publication remain separate required steps.

All new-domain secret and backup tasks share one two-worker admission counter; at most one is a backup task. Secret/signing tasks retain their 30-second limit; backup tasks have 60 seconds. Cancellation waits for actual worker termination before freeing capacity. A failed termination retains its charge. No legacy wallet worker, grant, budget, backup format or data changes as a consequence. Work may time out for large valid files with many expensive V3 sources; it never skips members or returns a partial backup.

Internal history archives use the distinct canonical `koincode-general-history-archive+jwe` direct A256GCM format. Its exact six-field plaintext shares the portable payload's state, history and coverage validators and includes references but no wrapping-key values, password or signed transaction bytes. The subkey uses the approved HKDF-SHA256 context, including the first sorted selected key reference, target identities, plan, archive and artifact. No extra random archive key is persisted. Reopening requires that same original source key under the genuine protected archive operation; missing material cannot be replaced with a newly generated key.

Archive metadata and size checks precede decryption; plaintext is parsed only after AEAD succeeds, then canonical encoding, full coverage, source identity and the original restore-plan commitment are checked. Encryption also verifies the selected source materials. Archive jobs use the existing new-domain pool, count as its single backup-class task and have the same 60-second bound and termination drain. Only the private protected restore owner may receive decrypted history. An encrypted/decrypted result does not prove file publication, active binding, current signing continuity or native authorization. Fixed artifact-file IO, native operation integration and real restore acceptance remain required. Portable and legacy backup formats reject archives, and archives reject their types.

The private restore-plan and initialization-record validators enforce strict bounded canonical JSON, immutable identities and ordered phases with idempotent same-phase readback. Restore plans bind the authenticated snapshot digest, original state/checkpoint and exact key coverage; a foreign installation preserves the original source identities and remains unknown for signing continuity. Same-installation target checks reuse the existing source/setup preservation rules and separately check the local state advance. These are format and snapshot checks, not journal continuity proofs, durable publication, native credentials or signing capabilities. Structural initialization parsing alone leaves its plan digest opaque; the separate association helper below verifies its approved digest semantics, while native enrollment still requires its real implementation. Ordinary create/open restrictions are unchanged.

The private initialization binding helper now defines the approved initialization plan digest independently of record phase. New initialization commits to a null recovery plan; first restore additionally binds its validated plan, target state and original archived domain identity. The root assignment must match the same initialization digest and identities. Structural record parsing alone does not establish this association or native enrollment; normal setup must not recompute it from a later current state.

The private first-restore bootstrap is a single-attempt Host substage under the original parent resources, not a production factory or authorization proof. It validates the existing bounded backup envelope, freezes the original H1 bootstrap_restore begin metadata, and requests the protected password only after the native scope is current. The fixed real preview worker shares the original two-task/single-backup owner. Its validated key-value-free preview produces deeply frozen existing RestorePlan, InitializationRecord and public Root reservation bodies; the target changes only the installation identity, retains source ownership/history commitments and starts with unknown signing continuity. The unchanged initialization digest uses the same private body helper. No backup text, password, wrapping-key value or entire history is returned with the candidate. Same-installation first restore is rejected by the existing rule, not reclassified to bypass it.

This substage retains the actual native loan until its original captured close function proves drainage; cancellation, expiry or a late callback cannot release the parent Root/UID/file resources or deliver a candidate. Dynamic scope-current checks still observe revocation. Unknown authorization or close results fence the instance and are not retried. Its maximum 180-second monotonic budget does not extend the native authentication, worker or parent deadlines. Actual signed code/profile/peer/window, fresh Root preparation, selected stable file descriptor, candidate-specific reference conflict checks, initialization and reauthenticated restore material admission remain the genuine parent/native actor responsibilities. No public entry, legacy Skill state, grant or budget is changed.

The private domain-binding parser checks the bounded canonical v1 body and its digest. Its association helpers distinguish first new, first archive-only restore and a same-installation successor with an exact previous digest and incremented revision. Live successors retain the previous live domain and additionally require the separate real continuity checks before publication. A candidate, parsed phase or matching head aggregate never grants signer authority or selects an active profile. Head aggregation reuses the current full signing-checkpoint validator, sorts detached metadata and does not change original registry/event ordering. Native first-use admission, artifact authentication, target resources, CAS/readback and view revocation remain required; these helpers perform no IO and are not public SDK/MCP or Skill APIs.

The private native assignment parser accepts only bounded binary plists with exactly the approved fields, current policy, canonical identifiers, matching positive UID and installation identity. It additionally checks the encoded top-level entry count so duplicate keys cannot be hidden by CoreFoundation dictionary decoding. It performs no filesystem, enrollment, locking, Keychain or authentication operations and confers no secret admission. Its expected identity parameters must eventually come from the verified native session, never a renderer assertion. No new public wallet entrypoint is added.

The private runtime backup coordinator freezes its exact selection and state/history plan before requesting native authorization. Authentication does not pre-lock normal work. After authorization, it immediately reserves setup, state and the same journal queue for a stable snapshot or returns busy; it never cancels another owner to obtain that lease. State changes during authentication invalidate the plan before source-key access. Each key read, worker completion and pre-publication capture rechecks the lifetime. Late keys are wiped and cancellation stops later reads. The coordinator's 180-second timer requests cancellation; already admitted bounded adapter work drains before its slot is freed. Native drain failure keeps the new-domain gates held and prevents storage shutdown underneath it.

File selection and publication are private trusted ports, not path-based renderer capabilities. The publisher must consume the exact opaque target once and prove durable byte/digest equality. Uncertain publication retains that reference and prevents another export in this coordinator. Known completed publication remains a completed file if cancellation arrives afterward. These ports have no production native session/file-dialog adapter yet; callback fixtures prove coordination only. Native enrollment, scoped key release, integration of the file component and restart recovery still require their actual adapters. Existing Skill processes, queues, grants and budgets do not reference these gates.

The private native backup-file component now implements the file-IO portion for a directory descriptor already selected by a trusted native operation. It duplicates that descriptor, binds its identity and kernel path, copies and hashes bounded ciphertext, and consumes its opaque target once. It exclusively creates a new 0600 file, clears and checks only that new file's ACL, writes bounded chunks, fsyncs the file, reads back the hash, fsyncs the directory and verifies the bytes again. Replaced entries/directories, symlinks, hardlinks, mode/ACL changes, cancellation and IO failure cannot overwrite an existing file or report success from a partial file. Created files are retained on uncertainty; destroying a target closes descriptors without deleting files. No CLI, renderer or key-release command invokes this component yet. The native session/file-dialog adapter, bounded supervision and restart recovery remain required; these functions do not establish authorization or real wallet acceptance. Permissions do not revoke existing handles or prevent future changes in a user-writable directory. Secrets remain protected by the authenticated outer backup encryption.

The same file core now has a private archive target constructor that accepts only a strict UUID and generates its `.jwe` name. The ordinary backup constructor still accepts only its original extension. Archive operations require a private current-user directory, bounded inventory of at most eight canonical regular-file entries, and available capacity before exclusive creation. Unknown entries, links, invalid ownership/mode/size or ACL on the directory are refused, never repaired or removed. Each scan uses a fresh directory file description so a prior enumeration cannot hide later entries. These checks are finite snapshots, not an atomic cross-process quota or proof that the supplied descriptor belongs to the right restore plan.

Existing archives are read once through a nonblocking, no-follow descriptor and checked as regular private files. The target retains that exact descriptor, identity, size and digest while its protected caller authenticates AEAD/header/plan. A one-use verify then requires the caller's matching ciphertext digest, rechecks the same named inode, fsyncs and reads back the file and directory without writing content. Failures preserve the file and return no durable success; read buffers belong to the caller, and target destruction requires its owner to drain first. COMPLETE proves file IO only. Native operation admission, fixed profile selection, cryptographic checks, binding publication and genuine restore acceptance remain separate requirements; no ordinary asset, Skill or SDK entry exposes these C functions.

The private `GeneralRecoveryRecordSession` coordinates the approved restore-plan, initialization and binding metadata formats. It fixes references from validated IDs, binds the supplied native scope, owns one active record session per protected connection and admits one command without a waiting queue. Missing metadata is not permission to create it: first prepare additionally requires the native new-record admission port, and the backend must enforce that exact operation itself. Parsed ready/reopened phases grant no native, source-key or signing authority. Initialization creation is never inferred from null. Idempotent readback preserves advanced phases and immutable plan bodies; stale or conflicting transitions cannot overwrite them.

Historical binding copies and the fixed first restore candidate contain the same bounded BindingV1 bytes. Their references and scope must match their bodies, and an existing body cannot be replaced or its artifact reselected. Candidate creation requires the original staged plan; known missing records still require native creation admission. Active binding publication never calls generic ProtectedStore.put. It requires the same candidate, its history copy, an explicit predecessor copy where applicable, and the current original plan and predecessor. An already identical active item is read back without repeating CAS; an advanced plan cannot be used to recreate a missing active item.

The optional private native CAS port is required for publication and is not a wire protocol or proof of genuine native admission. Its real implementation must enforce initialization, artifact, target-state, continuity and owner-lock facts itself and revoke old active views at publication even if the acknowledgment is lost. The client accepts only a void completion followed by exact active readback. Cancellation drains an admitted CAS and its metadata readback before releasing the slot; terminal delivery, including idempotent results, rechecks cancellation and lifetime. Exceptions, non-void responses or bad readback retain the original active reference and poison further writes on that connection. Only read inspection is allowed; recreating a JS session cannot authorize retry. No source key, signer, merchant request or Skill budget participates in these metadata methods.

Record writes read back their exact canonical bytes. Cancellation during an admitted write drains it and its one exact metadata readback, then returns no late success; the committed stage remains queryable. Unknown write/readback or corrupt stored data retains the original reference and disables further writes on that connection, including a rebuilt JS record session. Reads may inspect the same scoped facts. Close drains admitted IO before releasing the record owner; buffers are cleared. This in-process connection registry is not an anti-rollback or native identity root, and wrapping/replacing a JS backend cannot confer a new authenticated connection. Actual native enrollment, cross-restart unknown-result handling, durable archive/profile binding publication and restore credentials remain separate requirements. These metadata methods never access target source keys; the separate scoped staging method below shares their owner. The class is not exposed to ordinary asset IPC, SDK/MCP or Skill payment entrypoints.

The same private recovery-record owner now stages the selected restore wrapping keys in its existing command slot. It first reads the original protected plan and uses the unchanged backup worker to authenticate/decrypt the file and verify selected source materials. The complete payload digest and all plan associations are checked before any target-key access. Secret writes drain before returning, but secret readback is started only while the original operation remains live. Unknown connections may inspect the original plan metadata, not use this command to release an unknown key. Expiry cannot release an undrained owner or extend native authority. Closing registers its shared promise before abort callbacks, aborts this command's worker and waits for its result; genuine host/native drain remains required if worker termination cannot be confirmed. This private method adds no renderer/SDK/MCP/Skill route and returns only the original plan, never keys, payload or signing authority.

The private restore-state staging coordinator reuses the original checkpoint encoding and target repository without constructing a runtime, signing owner or active binding. Its frozen original plan must match the stored restore record. A void result is followed by exact checkpoint readback before writing an empty target projection. Existing projections must match exactly. Later restore phases are verification-only and missing targets are not recreated. Ordinary empty initialization and open-only failure rules are unchanged.

The private live-history staging component copies the original runtime's current full journal, intents, protected signed bytes and broadcast facts only for the stored keys_staged same-installation complete plan, under its existing snapshot lease. A mandatory genuine native admission precedes lazy target journal opening and each missing protected-reference write; no missing value alone authorizes creation. Target events must be an exact original prefix; existing protected bytes must match, absent source records must remain absent in the target, and the original registry is copied last. Partial/unknown effects restrict that same backend across JS owner replacement. Cancellation drains admitted IO and closes only its target repository, without secret readback after invalidation. One staging owner and one command occupy each target protection connection without a waiting queue; the same repository cannot be shared through another backend wrapper. Native exceptions, invalid completion/readback or projection write/readback failure retain uncertainty for that connection, including a rebuilt JS owner. Read inspection remains possible. The private port is not a session wire or native credential; fixtures cannot prove actual H1 admission, target-directory protection, source-key coverage or signing continuity. `@koincode/wallet/general` provides immutable general-wallet network identities and an independently owned read-only balance service for a trusted local utility. The service chooses only its built-in versioned RPC endpoints and cannot sign, broadcast or alter the existing SDK/MCP interfaces. Its network snapshots and failures are not payment evidence or legacy payment state. General-wallet process state and failures are owned separately from the legacy payment runtime.

Balance reads check chain identity before and after each snapshot attempt as well as the selected block's identity. A mismatch cannot be published as a new balance; a scoped previous result may remain explicitly stale. These checks do not authenticate an RPC or exclude a transient switch between the checks.

The isolated general-wallet RPC transport classifies system DNS `ENOTFOUND` and `EAI_AGAIN` as `BALANCE_DNS_UNAVAILABLE`; other resolver failures remain `BALANCE_UNAVAILABLE`, and cancellation remains `BALANCE_READ_CANCELED`. This gives the trusted local view a bounded diagnostic without exposing resolver details, changing legacy payment errors, or bypassing the system resolver. Cached results may still be returned as explicitly stale.

The general-wallet balance service may be given an explicit fixed RPC choice for its own read-only operations. Its candidate catalog is network-bound, and `probeRpc` performs chain and block checks without sending an account address. Choice identity participates in transport, throttle, flight and cache scopes. A trusted host must obtain explicit user confirmation before using a non-default candidate for account reads; catalog membership and a successful probe are not consent or evidence of an honest node. Defaults, legacy Skill RPC and manual signing RPC remain unchanged.

`GeneralBalanceService.inspectToken` inspects one explicitly selected account, network and token contract using the same isolated request scheduler. It verifies chain identity, nonempty contract code and `balanceOf` at a rechecked block; optional metadata can be absent. The result is untrusted display data, not a payment authorization, transfer guarantee, persisted asset or proof of a trustworthy RPC. The caller must discard results after the selection changes and render metadata only as text.

## System-protected desktop runtime

The trusted desktop owner calls `WalletRuntime.useSystemProtection()` before exposing its connection ports. This removes the product unlock prerequisite for all clients of that runtime; Keychain protection, grants, budgets, identities and final signing checks remain mandatory. The wallet page offers no explicit lock/unlock controls. Legacy SDK runtimes keep explicit unlock behavior unless their trusted owner opts in. In system-protection mode, legacy management lock/unlock requests reject with `EXPLICIT_LOCK_UNAVAILABLE` rather than falsely claiming a lock. Security events and shutdown still invalidate in-flight generations; they do not impose a new explicit-unlock requirement on later operations. This opt-in is not exposed to models or remote clients. Existing valid authorizations may continue to pay within limits while the system storage is available.

`@koincode/wallet/host` exposes only the same-process invocation bridge, public MCP tool descriptors and request/view types. It has no runtime, Signer, storage, native helper or Electron imports. Agent hosts use this thin entrypoint; wallet state and custody remain owned by the utility runtime. The descriptors are shared with the wallet MCP server rather than duplicated.

The wallet runtime is the only authority for wallet policy, grants, reservations and payment ledger state. Desktop, SDK and MCP adapters must share its instance and database. The core has no Electron, merchant, image or provider dependency.

`requests.approvals` is a trusted control-plane port. `prepare(handle, requestId, signal)` projects the exact unsigned frozen purchase, current wallet budget and body length/digest without header values, credentials, raw body or protected references. Its process-local approval ID binds the actual handle, request, quote reference/digest and default wallet; at most 32 live capabilities are retained, invalidated/replaced on demand, and the original quote must remain fresh. `decide` accepts only deny/once/session/persistent or continuation under an existing matching rule. Rules use one shared grant reducer and protected transaction. Each decision rechecks ownership, original cancellation, current quote/wallet and budget at admission; no model-supplied grant fields are accepted. Admission consumes the ID; storage failure is not retry permission. Cancellation after a rule's transaction was admitted may leave that rule persisted and requires explicit inspection/revocation.

Approval never unlocks or signs. `resume(handle, requestId, signal)` continues the original paid phase with the original body and business key; it does not repeat initial HTTP. The caller's abort reaches continuation admission and the final signing checks. A trusted `HostWalletConnections.connect` may inject a payment presenter: the original SDK call stays pending while it presents an approval, then resumes the same request. The optional fourth `resume` argument is an expected-wallet constraint supplied by a trusted display owner, never a wallet selector or model field. A presenter pins its first displayed wallet to the whole call. If the wallet becomes locked again during asynchronous preparation, the same live unsigned request can present once more for unlock under the existing rule; at most two presentations occur, with no new initial HTTP or automatic new grant. Same-owner backup restore merges missing authenticated request and retention history even when the request service is already initialized. Current request facts and deletion tombstones win; immutable identity or completion-evidence conflicts reject the state transaction. Imported nonterminal retentions become deletion intents, never executable or readable authority. A rejected merge leaves protected state unchanged, but the wallet remains locked and custody import may already have occurred. Foreign owners do not inherit these references.

The internal `ResponseRetentionOwner` binds precommitted references to immutable raw/context bytes and completion hashes. Bounded incomplete-record cleanup preserves valid ready data. Hosts must keep the service lease until operations settle. Local HTTP/runtime integration is described below; formal chat integration remains pending.

Local request bootstrap now supplies the same blob adapter as `retainedBlobs`. Publication binds `responseRetentionId`, so an older retained stage cannot overwrite a later result. Startup cleans at most one incomplete entry and close awaits initialization and running work before releasing storage. Custom environments without retention remain legacy-only and cannot open active retained inventory. SDK `recoverResponse(requestId, signal?)` and MCP `x402_recover_response` expose this bounded recovery through the same owner; chat integration remains pending. `EncryptedRequestBlobs.putRetained` accepts only this instance's response reservation and an exclusive canonical UUID. The local HTTP path invokes these operations through its retention owner; model tools do not receive these capabilities.

`ControlledHttp.send` receives a required synchronous `HttpContextCheck`. Trusted request environments now also require `checkOutbound(client, context, effect)`, synchronously returning literal `true` only while the host's exact outbound approval remains valid. `OutboundEffect` is exported through the Node entrypoint: `prepare_http`, `dns`, `connect`, `submit`, or `sign`. HTTP checks run before transport entry and at the transport boundaries. Signing checks follow the existing builder/constraint path into custody's final check after asynchronous key loading. Checks may repeat before and after signing; they are not consumable tickets or counts of effects. No body, credential value or signature is passed to this synchronous port. The trusted environment must also supply response inspection. Local bootstrap uses bounded, cancellable workers so untrusted response decoding does not block wallet lock events. Each `RequestHttp.execute` owns one HTTP phase and its inspection. Inspection uses the captured values and existing secret-derivation rules, not a second protected-store lookup after HTTP. Current credential metadata, session, generation and cancellation are still checked before and after inspection; captured secrets never grant authority. Only the HTTP status leaves the internal execution method after publication, and the secret snapshot is absent from persistent request records and client views. This preserves inspection when a subsequent protected read would fail or differ, but does not establish physical erasure of JavaScript strings. Retained HTTP recovery binds the original snapshot under protection as described above.

`openLocalWalletRequests` opens one runtime and enables requests while it retains the same service lease. Schema 2 transactionally adds transport records after checking the authoritative schema-1 layout and taking a SQLite snapshot. Empty M2 transport state preserves existing commitment bytes. Request, response and payload blobs are encrypted separately; tombstones remain when contents expire. Recovery changes the management epoch, invalidates old token/credential authority and blocks incomplete old operation namespaces; newly registered clients create provably new namespaces. HTTP completion, chain spending and business delivery remain separate facts.

Schema 3 adds an indexed response-retention journal after verifying the authoritative schema-2 layout and durably syncing a private pre-upgrade snapshot. Empty retention inventory is omitted from transport state so old protected commitments stay identical. Nonempty records participate in the existing control digest; identities, deadlines and raw/context references are immutable, completion requires bounded lengths and digests, and deletion cannot be reversed or erased from history. References cannot overlap other retention records or ordinary request/response/quote/payload/body blobs. The internal journal records writing, ready, deleting and deleted; it performs no storage IO and its metadata alone is not read authorization or proof of key removal. Only a trusted cleanup owner with confirmed IO may complete deletion. The HTTP retention owner enforces original-secret context binding, live access, write draining and cleanup outcomes; the journal is not a public tool. Backups with any retention history use history version 2, while legacy history without it remains version 1. Same-owner restoration invalidates retained material into deleting without reviving deleted tombstones; another owner receives no source retention capabilities. Older schema-2 code rejects schema 3, and older history-version-1 readers reject version 2. Downgrade must not overwrite an advanced wallet with a pre-upgrade snapshot.

`requests.controls` and `requests.resume` are trusted host actions and are absent from the public client and MCP tools. They may continue only a provably unsigned frozen purchase within the current owner/client/epoch. A persisted unsigned refresh exclusively fences its parent through completion, unknown outcome and result consumption. A possibly signed intent follows chain reconciliation, never this unsigned path. A fresh once approval is required after expiry/refresh; persistent rules are reevaluated. Public duplicate operations only observe the existing result.

HTTP response admission caps encoded body bytes at 72 MiB and decoded body bytes at 64 MiB. `PinnedHttp` uses an asynchronous, backpressured pipeline with a wire counter, optional gzip/deflate/Brotli decoder and a bounded collector. Cancellation destroys the pipeline; incomplete HTTP, unknown encodings and decompression failures cannot publish partial bytes. Only complete pipeline settlement releases the HTTP slot after a response starts. These are body-byte limits, not total RSS or disk guarantees: collecting, IPC, hashing and encryption still allocate/copy. The same decoded limit applies to inspection, protected blobs, retention, relocation and SDK reads; response-stage reservations scale with it. Existing 32 MiB blobs remain readable, but older readers cannot be assumed to accept newly stored larger blobs. New frozen requests bind a trusted 20-minute HTTP phase budget; legacy frozen requests without this field retain 120 seconds. Each initial/paid phase has an independent deadline; the 50-minute action ceiling never expands a phase. Approval/preparation, signing preparation and response processing each have separate 120-second bounds. Quote freshness, permit and authorization lifetimes are unchanged. Internal automatic reconciliation keeps its shorter ten-minute task ceiling. SDK request accepts an optional cancellation signal. MCP advertises stage and action ceilings; external hosts must configure their call timeout appropriately or deliberately cancel earlier. No timeout permits reissuing a purchase. Timers and wall/monotonic boundary checks do not prove instantaneous cancellation of blocked OS IO.

The public SDK journals trusted host action IDs and streams complete opaque response bytes in chunks of at most 64 KiB with ownership rechecked. MCP calls attach the durable UUID at `_meta["io.koinelix.wallet/operationId"]`; models cannot supply identity or payment grants through arguments. MCP exports use a host-approved opaque destination and never overwrite an existing file. Known credential/signature echoes are replaced by an explicit redacted response and marked `sensitiveRedacted`. Standard MCP cancellation and explicit request cancellation stop future steps without claiming to undo remote effects.

Each `HostWalletConnection` owns one `ResponseExporter`, shared with that connection's `WalletToolCalls`. The trusted `BlobStore` requires synchronous `reserveResponse()` returning an opaque local `ResponseReservation` with `put` and idempotent `release`. The request owner reserves initial capacity before HTTP and separate paid capacity before signing, and writes response/quote/payment payload through that reservation. Missing or asynchronous reservation adapters fail closed. Local encrypted storage owns a single 1536 MiB logical inventory plus reservations across clients: ciphertext bytes including its 28-byte envelope, plus 4096 bytes per file entry. This is not an OS disk, Keychain, or RSS limit. A stage reserves two maximum bodies and four 1 MiB metadata allowances with overhead (selected quote, payment payload, retained HTTP context and returned quote); the service, HTTP transport, response inspector and blob budget each admit at most ten concurrent HTTP stages when storage permits. Host payment-only signing reserves two metadata entries of up to 1 MiB each in the same inventory for the selected quote and signed header. This reservation can coexist with all ten HTTP stages and cannot write retained response bodies. Existing files, partial writes and orphans count after bounded startup inventory; over-budget stores still allow reading existing valid blobs but reject new capacity. Failed writes retain their full charge until exact confirmed cleanup or the next inventory; release alone refunds only unused reservations. A durable empty file precedes key creation; incomplete files cannot be read as results. The adapter must be used under the runtime's single writer lease. Capacity accounting alone does not delete legacy orphan keys, recover raw responses, enlarge the current body/HTTP limits, or guarantee that disk writes cannot subsequently fail. A post-signing failure preserves the original payment exposure. Cancellation can leave bounded underlying network/inspection cleanup in progress; stage slots are admission accounting, not proof that every OS resource has exited.

Storage admission also reserves file entries: the shared limit is 100,000 used or reserved entries, six per response stage and one per direct metadata write. Spending transfers one entry before IO; failed writes retain that entry until the next inventory. An older directory exceeding the bounded scan is opened read-only with an over-limit sentinel, not a purported complete byte count. It cannot obtain new reservations or writes; valid retained blobs can still be read by reference. No historical files are deleted to satisfy the limit.

The primitive does not serialize concurrent writers, establish durable tombstones or prove physical erasure. Account names must never be reused. Older software must not open schema 4 or replace it with an old backup. Complete host task authority, MCP integration, journal recovery tooling, native trust and actual Keychain validation remain pending. A compromised protected store rolled back together with the wallet is outside the guarantees of this local implementation.

# Payment-only public client (2026-10-29)

`createAuthenticatedPaymentClient` is exported by `@koincode/wallet/node`. The optional KoinCode script launcher is host integration and is not implemented in this wallet module.

Payment-only records explicitly commit `hostPayment.paymentOnly: true`. They cannot be interchanged with legacy host execution records. The public client persists the caller operation mapping in the existing protected wallet request state, not a second business database. Reusing an operation with different content fails, and an uncertain/signed authorization cannot be resubmitted.

Trusted management may explicitly unlock with `scope: "application"` after user authentication. This in-memory application session has no idle or hard timer. The trusted display represents such a live session as `locked: false, unlockRemainingMs: null`.

A protected-store failure, an ambiguous signature, a failed unsigned release, or an already ended session does not receive this exception. Payment reconciliation accepts an optional transaction hash lookup hint on the original owned payment (`reconcile_payment`, and MCP `x402_reconcile`). The internal `GeneralSetupSession` is a protected-host-only dispatcher over the existing `GeneralSetupCoordinator`. It is not exported by the read-only general entry or any model/payment API. The private GeneralRestoreArchiveReader connects the existing original-plan record session, bounded archive worker and retained native archive-file handle.
